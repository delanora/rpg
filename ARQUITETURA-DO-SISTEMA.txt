================================================================================
0) RESUMO OPERACIONAL (leia primeiro)
================================================================================

O Codex do Aventureiro é uma aplicação web MULTIUSUÁRIO de mesa única para D&D 5e
(PHB 2014). Um processo Node.js único serve, na MESMA porta:

  • a API REST em /api/*;
  • o canal WebSocket (Socket.io) em /socket.io;
  • o build estático do frontend React (client/dist) na raiz /, com fallback SPA;
  • os arquivos enviados em /uploads/*;
  • health check em /api/health.

Persistência: PostgreSQL via Prisma (modelagem híbrida: colunas para campos
escalares + JSONB para coleções grandes, validadas por Zod na aplicação).

Dois papéis: PLAYER (uma única ficha, a própria) e MASTER (painel de controle com
fichas de todos, bestiário, regiões/localidades, catálogo de itens, combate,
compêndio e configurações da mesa).

REGRA ARQUITETURAL CENTRAL: TODA ESCRITA DE DOMÍNIO ACONTECE POR HTTP.
O WebSocket é canal EXCLUSIVO DE NOTIFICAÇÃO (servidor → cliente). Os handlers
cliente→servidor existem apenas para entrar/sair de salas. Isso elimina dois
caminhos de gravação divergentes.

Consequência prática: cada escrita HTTP persiste, recalcula os valores derivados
e então publica um evento em tempo real pelo `broadcaster`. Falha na publicação
NUNCA derruba a requisição já persistida (todo `publish*` está em try/catch).

Comandos (package.json):
  npm run dev                 → tsx watch src/index.ts
  npm run build               → tsc -p tsconfig.json  (emite dist/)
  npm start                   → node dist/index.js
  npm run typecheck           → tsc --noEmit (servidor)
  npm --prefix client run typecheck
  npm --prefix client run build      → vite build (client/dist)
  npm run prisma:generate | prisma:migrate | prisma:deploy | prisma:studio
  npm run db:push             → prisma db push
  npm run create-master       → cria/atualiza conta MASTER por CLI
  npm run migrate:attack-damage → converte o dano textual dos ataques em estruturado
  npm run migrate:item-weapons  → completa os campos de arma dos itens (tipo/categoria)
  npm run smoke               → tsx src/scripts/smoke-realtime.ts

EM PRODUÇÃO O SERVIÇO systemd EXECUTA `dist/`. Alterar `src/` sem `npm run build`
não tem efeito nenhum.

================================================================================
3) BOOTSTRAP E CICLO DE VIDA DO PROCESSO
================================================================================

Sequência exata em src/index.ts:
  1. `createApp()` monta o Express (sem `listen`).
  2. `createServer(app)` cria o http.Server.
  3. `createRealtimeServer(httpServer)` cria o Socket.io sobre o MESMO http.Server
     (HTTP e WebSocket na mesma porta) e registra o broadcaster no hub.
  4. `httpServer.listen(env.PORT)`.
  5. Loga "🐉 Codex do Aventureiro — <NODE_ENV>" e as URLs.

Encerramento gracioso (SIGINT/SIGTERM — o systemd envia SIGTERM):
  • temporizador de segurança de 10 s (`unref`) que força `process.exit(1)`;
  • `io.close()` → `httpServer.close()` (aguardado) → `prisma.$disconnect()`;
  • `process.exit(0)`.

Carga inicial: `dotenv/config` é importado no topo de src/config/env.ts, então o
.env é lido antes de qualquer leitura de variável. Se a validação Zod falhar, o
processo imprime o mapa de erros e sai com código 1 (nunca sobe parcialmente).

4) VARIÁVEIS DE AMBIENTE (src/config/env.ts — validadas por Zod)
================================================================================

  NODE_ENV            'development' | 'test' | 'production'   (default: development)
  PORT                inteiro positivo                          (default: 3000)
  DATABASE_URL        string não vazia                          (OBRIGATÓRIA)
  CORS_ORIGIN         default '*' — '*' libera tudo; senão lista separada por vírgula
  JWT_SECRET          mínimo 16 caracteres                      (OBRIGATÓRIA)
  JWT_EXPIRES_IN      default '7d' (passado ao jsonwebtoken)
  MASTER_INVITE_CODE  mínimo 4 caracteres, OPCIONAL. Sem ela, é impossível se
                      cadastrar como MASTER pela API (só pela CLI create-master).

Derivado: `corsOrigins` = '*' ou array de origens. Usado tanto no Express quanto
no Socket.io, sempre com `credentials: true`.

ATENÇÃO DE IMPLANTAÇÃO (documentada no unit systemd): o .env NÃO deve definir
NODE_ENV, porque em systemd o EnvironmentFile tem precedência sobre a diretiva
`Environment=`. O unit define `Environment=NODE_ENV=production` e o .env define
DATABASE_URL/PORT/JWT_SECRET/MASTER_INVITE_CODE/CORS_ORIGIN.

deploy/grimorio.service (resumo):
  After=network-online.target postgresql.service
  Requires=postgresql.service
  WorkingDirectory=/var/www/rpg
  EnvironmentFile=/var/www/rpg/.env
  Environment=NODE_ENV=production
  ExecStart=/usr/bin/node dist/index.js
  KillSignal=SIGTERM   TimeoutStopSec=15
  Restart=on-failure   RestartSec=3

5) CAMADA HTTP (src/http/app.ts)
================================================================================

Ordem EXATA dos middlewares (a ordem é semântica):
  1. app.disable('x-powered-by')
  2. helmet({ crossOriginResourcePolicy: 'cross-origin', contentSecurityPolicy: {
       defaultSrc 'self'; scriptSrc 'self'; styleSrc 'self' + 'unsafe-inline';
       imgSrc 'self' + data: + blob:; connectSrc 'self' + ws: + wss:;
       upgradeInsecureRequests: null } })
     — `upgradeInsecureRequests` é desativado de propósito: o sistema é acessado
       por IP em HTTP simples e o upgrade forçado quebraria a página.
  3. cors({ origin: corsOrigins === '*' ? true : corsOrigins, credentials: true })
  4. express.json({ limit: '8mb' })
     — as fichas são pequenas; o limite alto existe para upload de imagem como
       data URL (base64) dentro do JSON.
  5. express.static(UPLOADS_DIR, { maxAge: '7d', immutable: true }) em /uploads
  6. app.use('/api', apiRouter)
  7. SE `client/dist` existir:
       express.static(clientDist);
       fallback SPA: para GET cujo path NÃO comece com /api nem /socket.io,
       envia client/dist/index.html.
  8. notFoundHandler → 404 { error: 'NOT_FOUND', message }
  9. errorHandler → status do HttpError (ou 500). `< 500` ⇒
     { error: 'REQUEST_ERROR', message }. `>= 500` ⇒ loga e devolve
     { error: 'INTERNAL_ERROR', message }. Em development, inclui `stack`.

Caminho de uploads: `UPLOADS_DIR = <raiz do projeto>/uploads`, resolvido a partir
de `import.meta.url` (vale tanto em `src/lib` quanto em `dist/lib`). Idem para
`clientDist = <raiz>/client/dist`.

Formato de erro padrão da API:
  { "error": "CODIGO", "message": "texto em pt-BR", "issues"?: {campo: [msgs]} }
  Códigos: VALIDATION_ERROR (400), UNAUTHORIZED (401), FORBIDDEN (403),
  NOT_FOUND (404), INTERNAL_ERROR (500), TOO_MANY_REQUESTS (429).
  Erros de negócio usam HttpError(status, mensagem) e caem como REQUEST_ERROR com a
  mensagem literal (ex.: 409 "Você já usou esta liberação de Level Up.").

ROTAS MONTADAS (src/http/routes/index.ts, em ordem):
  /health /auth /users /characters /creatures /regions /localities /items
  /game /compendium /dice /uploads /presentation /combat

6) AUTENTICAÇÃO, AUTORIZAÇÃO E IDENTIDADE DO ATOR
================================================================================

REGISTRO (POST /api/auth/register, LIMITADO por rate limit)
  Corpo: { username, displayName, password, masterInviteCode? }  (Zod: auth.schema.ts)
  Papel default PLAYER. Se `masterInviteCode` vier: precisa ser IGUAL a
  env.MASTER_INVITE_CODE — senão 403 "Código de mestre inválido."; se bater, vira
  MASTER. Username duplicado ⇒ 409. Senha é hasheada com bcrypt (custo 12).
  Resposta 201: { token, user: PublicUser }.

LOGIN (POST /api/auth/login, LIMITADO)
  Usuário inexistente e senha errada devolvem A MESMA mensagem (401 "Usuário ou
  senha inválidos.") para não revelar a existência de contas.
  Resposta 200: { token, user }.

RATE LIMIT (auth.routes.ts, `authLimiter`) — aplicado SÓ a /register e /login:
  janela 15 min; limite 30 em produção e 100 fora de produção; standardHeaders true.
  Estado EM MEMÓRIA do processo ⇒ um restart do serviço zera o contador.
  [NOTA OPERACIONAL] Isso é relevante para o smoke test: rodar `npm run smoke` duas
  vezes seguidas pode devolver 429 no login; reiniciar o serviço limpa.

TOKEN (src/lib/jwt.ts)
  HS256, payload TokenPayload = { sub: userId, username, displayName, role },
  validade JWT_EXPIRES_IN (default 7d).

MIDDLEWARE `authenticate` (auth.middleware.ts)
  Lê `Authorization: Bearer <token>`; verifica a assinatura; E CONFERE A CONTA NO
  BANCO a cada requisição (`prisma.user.findUnique`). O `req.user` é montado a
  partir do BANCO, não do token. Efeitos deliberados:
    • conta excluída perde o acesso NA HORA (o JWT continuaria válido até expirar);
    • mudança de papel vale sem novo login.
  401 sem token/assinatura inválida; 401 se a conta não existe mais.

MIDDLEWARE `requireRole(...roles)`
  Usado sempre DEPOIS de `authenticate`. 401 sem req.user; 403 se o papel não está
  na lista.

REGRA TRANSVERSAL — O ATOR NUNCA VEM DO CORPO DA REQUISIÇÃO.
  `actorFrom(req)` sempre monta { userId: req.user.sub, ... } a partir do token. O
  servidor carimba identidade em: autor da rolagem, editedBy da ficha, nome de quem
  apresenta a imagem, ownerUserId do combatente. Não há como personificar outro
  usuário enviando ids no payload.

Os dois únicos canais públicos (sem `authenticate`): POST /api/auth/register e
POST /api/auth/login. Todo o resto é autenticado; os sub-roteadores aplicam
`requireRole('MASTER')` no próprio roteador (creatures, regions, localities) ou por
rota (characters, items, game, dice, combat, presentation, uploads).

7) MODELO DE DADOS (prisma/schema.prisma → PostgreSQL)
================================================================================

FILOSOFIA: modelagem HÍBRIDA. Campos escalares muito consultados em colunas;
coleções grandes em JSONB validado por Zod na aplicação (sem dezenas de tabelas
auxiliares). Toda tabela usa `@@map` para nome snake_case; todo id é `cuid()`
exceto GameConfig (chave fixa "main").

7.1 GameConfig  → tabela `game_config` (LINHA ÚNICA, id = "main")
    id             String  @id @default("main")
    levelUpRelease Int     @default(0)   // contador de liberações de Level Up
    startingLevel  Int     @default(1)   // nível em que a mesa começa (1..20)
    masterNotes    String  @default("")  // anotações PRIVADAS do mestre (<= 20.000)
    extraCoins     Boolean @default(false) // exibe PL (pp) e PE (ep) no bloco de moedas
                                           // das fichas; os valores existem sempre
    updatedAt      DateTime @updatedAt

    Invariante: `masterNotes` NÃO entra no GameConfigDto. O GET /api/game é
    acessível ao JOGADOR (a ficha lê o contador de liberações), então as
    anotações só trafegam por /api/game/notes, exclusiva de MASTER (§8.14).

7.2 enum Role { PLAYER, MASTER }

7.3 User → tabela `users`
    id String @id @default(cuid()) · username String @unique · displayName String
    passwordHash String · role Role @default(PLAYER) · createdAt · updatedAt
    character Character?  (relação 1:1; `Character.userId` é @unique)
    @@index([role])
    Invariante: UMA ficha por usuário; e a conta do MASTER não tem ficha.

7.4 Character → tabela `characters`
    id String @id @default(cuid())
    userId String @unique  →  User (onDelete: Cascade)
    creationFinalized Boolean @default(false)
    creationDraft Json @default("{}")   // rascunho do assistente de criação
    name String @default("Novo Personagem") · race String @default("")
    classes Json @default("[]")   // [{ classKey, subclass, level }]
    background String · alignment String · experience Int @default(0)
    lastLevelUpRelease Int @default(0)  // última liberação USADA por esta ficha
    levelHistory Json @default("[]")    // o que CADA nível concedeu: PV ganho
                                        // { rolled, die, gained, conDelta, total },
                                        // abilityIncreases, feat { id, name },
                                        // choices, subclass, skills e proficiências.
                                        // É o que permite ao mestre REVERTER um nível
                                        // (§12.5). Níveis anteriores à migração

9) CAMADA DE TEMPO REAL (Socket.io)
================================================================================

Criação: em `createRealtimeServer`, sobre o MESMO http.Server.
  transports: ['websocket', 'polling']; CORS idêntico ao do Express.

HANDSHAKE (`socketAuth`, aplicado com `io.use`)
  Token aceito de `socket.handshake.auth.token` (usado pelo frontend) OU
  `?token=` na query string (para ferramentas de CLI).
  Além de verificar a assinatura, CONSULTA A CONTA NO BANCO: token de conta
  excluída não abre socket. Em sucesso popula `socket.data` =
  { userId, username, displayName, role }. Falha ⇒ `next(new Error('UNAUTHORIZED'))`.

SALAS (rooms.ts) — um socket entra em:
  'table:main'            (TABLE_ROOM) → todos os conectados, jogadores + mestre
  `user:${userId}`        (userRoom)   → todas as sessões/abas do mesmo usuário
  'role:masters'          (MASTERS_ROOM) → só se role === 'MASTER'
  Cliente→servidor: 'table:join'/'table:leave' com `tableId?` opcional entram/saem
  de `tableRoom(tableId ?? TABLE_ROOM)` — gancho para mesa múltipla futura.
  [LACUNA/HIGIENE] `combatRoom(tableId)` = `combat:${tableId}` está exportado mas
  NÃO é usado: os eventos de combate vão para a mesa toda (toTable) e para a sala
  dos mestres, com filtragem de VISIBILIDADE no payload, não por sala.

AO CONECTAR, o servidor:
  1. entra nas salas;
  2. `registerConnection` (presença em memória: userId → Set<socketId>);
     só quando o usuário passa a ter a PRIMEIRA conexão é que a presença é publicada;
  3. emite `connection:ready` { socketId, connectedAt, user: {userId, username, role} };
  4. se houver APRESENTAÇÃO ativa, emite `presentation:shown` para o socket novo;
  5. se houver JANELA DE DADOS ativa, emite `dice:active` { active: true, ... }.

AO DESCONECTAR: `unregisterConnection`; se foi a última aba do usuário:
  `clearActiveRollFrom(userId)` (tira a faixa "está rolando") e republica presença.

BROADCASTER (broadcast.ts) — API usada pelos módulos de domínio:
  toUser(userId, evento, payload)      → sala user:<id>
  toMasters(evento, payload)           → sala role:masters
  toTable(evento, payload)             → sala table:main
  toPlayers(evento, payload)           → table:main EXCETO role:masters
  disconnectUser(userId)               → io.in(userRoom).disconnectSockets(true)
  presence()                           → presence:update { online: OnlineUser[] }
  Acesso pelo singleton `getBroadcaster()` (hub.ts); se a camada não foi
  inicializada, lança erro — o que aconteceria apenas em uso fora do bootstrap.

ESTADO EFÊMERO EM MEMÓRIA (não vai ao banco, some no restart):
  • presença (presence.ts);
  • apresentação de imagem atual (presentation.service.ts);
  • janela de dados ativa + histórico de até 100 rolagens (dice.service.ts).
  Motivo: mesa única em um processo; guardar em memória permite REENVIAR o estado a
  quem conectar no meio (reconexão, recarga de página).

10.1 ATRIBUTOS E GERAL
  ABILITY_KEYS = strength, dexterity, constitution, intelligence, wisdom, charisma
  Limites: atributo 1..30; nível 1..20.
  Modificador: floor((score − 10) / 2).
  Bônus de proficiência: 2 + floor((nível − 1) / 4), com nível limitado a 1..20
    → +2 (1–4), +3 (5–8), +4 (9–12), +5 (13–16), +6 (17–20).
  XP para o próximo nível: tabela fixa do PHB (300, 900, 2.700, 6.500, 14.000,
    23.000, 34.000, 48.000, 64.000, 85.000, 100.000, 120.000, 140.000, 165.000,
    195.000, 225.000, 265.000, 305.000, 355.000); null no nível 20.
  Capacidade de carga: Força × 7,5 (kg) — variante métrica (2 lb = 1 kg).
  Iniciativa: modificador de Destreza + `initiativeBonus` avulso.
  Deslocamento padrão: 9 m.
  Percepção passiva: 10 + total de Percepção.
  CD de magia: 8 + proficiência + mod. do atributo de conjuração.
  Bônus de ataque mágico: proficiência + mod. do atributo de conjuração.
  Magias preparadas — calculadas POR CLASSE (`preparedSpellCountFor`), com o
    atributo e o nível de cada uma:
      • completo/preparado (Clérigo SAB, Druida SAB, Mago INT): max(1, mod + nível).
      • meio-conjurador preparado (PALADINO CAR): max(1, mod + floor(nível/2)) e
        ZERO antes do 2º nível (a conjuração começa no 2º).
      • conjuradores CONHECIDOS (Bardo, Feiticeiro, Bruxo, Patrulheiro e os
        terço-conjuradores Trapaceiro/Cavaleiro Arcano): null — usam a tabela de
        magias conhecidas, não a fórmula.
    Exposto em `CharacterDto.classes[].spellcasting.preparedCount`.
    NÃO existe total único no DTO: em multiclasse cada classe prepara as suas.

10.2 PERÍCIAS (18) e SALVAGUARDAS
  `normalizeSkills` garante as 18 chaves com { proficient, expertise } booleanos;
  `normalizeSaves` garante os 6 atributos booleanos. Total de uma perícia =
  modificador + (proficiente ? prof × (expertise ? 2 : 1) : 0). Expertise só conta
  com proficiência.

10.3 CLASSE DE ARMADURA (nunca é valor fixo)
  `armorClass` no banco é apenas o OVERRIDE do mestre (0/ausente = automático).
  Peças lidas do INVENTÁRIO EQUIPADO (slot ≠ null):
    • Armadura: categoria 'Armadura' no slot 'chest' com `armorType` e
      `baseArmorClass` cadastrados. Sem esses campos, o item não vira armadura.
      Leve: base + mod. DES inteiro · Média: base + min(mod. DES, 2) ·
      Pesada: só a base (bônus de Destreza = 0).
    • Escudo: qualquer item da categoria 'Escudo' equipado soma `armorClassBonus`.
    • Bônus mágicos: `armorClassBonus` dos DEMAIS itens equipados.
  Sem armadura: vale a MAIOR entre 10 + mod. DES e as fórmulas de Defesa sem
  Armadura das classes. As fórmulas NÃO se acumulam.
    – Bárbaro: 10 + DES + CON
    – Monge: 10 + DES + SAB, EXIGINDO nenhum escudo equipado
    – Feiticeiro (Linhagem Dracônica): 13 + DES
  Depois somam-se escudo + bônus mágicos. Se houver override do mestre, ele
  substitui o automático (`value = override ?? automatic`).
  O DTO expõe `armorClass` (efetiva) e `armorClassOverride` (null = automático), e
  `derived.armorClass` traz o detalhamento (automatic, armor, dexterityBonus,
  shieldBonus, magicBonus, unarmoredLabel).

10.4 PONTOS DE VIDA
  Nível 1 (primeira classe): max(1, dado de vida + mod. CON).
  Level Up: ganho = max(1, dado rolado|média + mod. CON JÁ ATUALIZADO pelo ASI do
    mesmo nível). Média = floor(dado/2) + 1 (d6→4, d8→5, d10→6, d12→7).
  RECÁLCULO RETROATIVO DE CON: sempre que o modificador de CON muda (patch ou
    Level Up), o PV passa a valer como se o novo valor existisse desde o nível 1:
      delta = (mod novo − mod antigo) × nível total ANTERIOR
    O delta entra no hpMax E no hpCurrent; ao reduzir, hpCurrent nunca fica negativo.
  O dado de vida do Level Up é rolado NO SERVIDOR (crypto.randomInt) — o cliente só
  escolhe 'roll' ou 'average'.

10.5 REGISTRO DE CLASSES (classes/)
  12 classes: barbarian, bard, cleric, druid, fighter, monk, paladin, ranger,
  rogue, sorcerer, warlock, wizard.
  ClassDefinition = { key, name, hitDie, savingThrows[2], subclassLevel,
                      spellcasting{type,ability,learning}, features[], subclasses[] }
  SpellcastingType = none|full|half|third|pact · SpellLearning = known|prepared|none
  NÍVEL DE ESCOLHA DE SUBCLASSE (`subclassLevel`):
    cleric 1 · sorcerer 1 · warlock 1 · druid 2 · wizard 2 · todas as outras 3.
  SUBCLASSES CADASTRADAS: TODAS as do PHB — cleric (7 domínios), warlock (3 patronos),
    barbarian (2), bard (2: Colégio do Conhecimento e da Bravura), druid (2),
    fighter (3: Campeão, Mestre da Batalha, Cavaleiro Arcano), monk (3), paladin (3:
    Devoção, Anciões, Vingança), ranger (2: Caçador e Senhor das Feras), rogue (3),
    sorcerer (2), wizard (8 escolas).
    Mestres da Batalha expõe as 16 manobras; o Caçador declara as 4 escolhas do
    arquétipo (Presa do Caçador no 3º, Táticas Defensivas no 7, Multiataque no 11 e
    Defesa Superior no 15); o Colégio da Bravura concede `proficiencies`
    (armaduras médias, escudos e armas marciais) somadas às da classe quando a
    subclasse é escolhida, e o Cavaleiro Arcano declara a conjuração de terço
    (`spellcasting: { type: 'third', ability: 'intelligence', learning: 'known' }`).
  FEATURES: cada feature tem
    { id, name, level, description, effect? | effects?, choice? }.
    Efeitos suportados (ClassFeatureEffect.type): bonus, resource, save, expertise,
    sneakAttack, toggle, resistance, speed, damageBonus, critDice, unarmoredDefense,
    martialArts, wildShape, hpBonus, abilityBonus, armorClass, saveBonus,
    halfProficiency, critThreshold, other.
    Recursos com contador aceitam: max fixo, maxByLevel[], perLevel (× multiplicador),
    soma do modificador de um atributo (abilityMod) e piso do total (min).
  ESCOLHAS DE CARACTERÍSTICA (`choice`): uma feature pode declarar
    { count, options[{ key, name, description, effect? }], level?, prompt?,
      allowRepeat?, apply? }. O valor vive em `classState.choices[featureId] = [chaves]`
    (JSONB, sem migração). Quem valida é `resolveFeatureChoices` (quantidade,
    opção existente, sem repetir e só no nível em que a escolha é feita) — usada
    no Level Up (novo nível da classe) e no passo 5 do assistente (nível 1).
    `pendingFeatureChoices`/`featureChoiceInfo` alimentam a interface: o DTO expõe
    `classes[].featureChoices` (incluindo as da SUBCLASSE já escolhida, graças a
    `featuresWithSubclass`), `classOptions[].featureChoices` (nível 1) e
    `classOptions[].subclassChoices` (com o nome da subclasse) — este último é o
    que mostra a escolha quando a SUBCLASSE é escolhida no mesmo nível em que ela
    já pede uma escolha (Caçador no 3º, Colégio do Conhecimento no 3º).
    `apply: 'skill'` faz as chaves escolhidas virarem proficiência de perícia
    (Colégio do Conhecimento: 3 perícias).
    FEATURES COM ESCOLHA: Estilo de Luta (fighter nv 1 — id 'fighter-fighting-style',
    paladin nv 2, ranger nv 2), Inimigo Favorito (ranger nv 1, +1 no 6 e no 14),
    Explorador Nato (ranger nv 1, +1 no 6, +2 no 10), Estilo de Luta Adicional
    (Campeão nv 10), Manobras (Mestre da Batalha nv 3, +2 no 7/10/15), Estudante da
    Guerra (Mestre da Batalha nv 3, 1 ferramenta de artesão), Proficiências
    Adicionais (Colégio do Conhecimento nv 3, 3 perícias) e as 4 do Caçador. Só a
    opção Defesa tem efeito automático (+1 CA com armadura); as demais são escolha
    informativa (Fase 5).
  EFEITOS NUMÉRICOS NO DERIVED:
    • armorClass (+1, requiresArmor) → `derived.armorClass.classBonus`, SOMADO só
      com armadura vestida (escudo não conta) e nunca duas vezes entre classes;
    • saveBonus (abilityMod + minValue) → `derived.saveBonus`, somado a TODAS as
      salvaguardas (Aura de Proteção: mod. de CAR, mínimo +1);
    • halfProficiency (target 'checks' | 'physicalChecks') → metade da proficiência
      em testes de habilidade SEM proficiência, inclusive a iniciativa. `round`
      decide o arredondamento ('down' no Pau para Toda Obra do bardo, 'up' no
      Atleta Extraordinário do Campeão); dois efeitos no mesmo teste não somam:
      vale o maior;
    • critThreshold (value) → `derived.critThreshold` (padrão 20): o ataque do
      combate acerta criticamente com d20 >= limiar (Campeão: 19 no 3º e 18 no 15º).
      Crítico sempre acerta e o 1 natural sempre erra; o MENOR limiar prevalece.
  FEATURES CADASTRADAS POR CLASSE (PHB 2014): barbarian, druid, fighter, monk,
    paladin, ranger, rogue, sorcerer, wizard, bard.
  [LACUNA CONHECIDA] cleric e warlock têm `features: []` (só as subclasses):
    faltam Canalizar Divindade/Destruir Mortos-Vivos/Intervenção Divina (clérigo) e
    Invocações Místicas/Dádiva do Pacto/Arcanum Místico/Mestre Místico (bruxo).
    O ladino não tem a Gíria de Ladrão (nível 1, texto puro).
  PERÍCIAS DE CLASSE (CLASS_SKILL_CHOICES): quantas e de qual lista —
    barbarian 2, bard 3 (lista vazia = qualquer uma das 18), cleric 2, druid 2,
    fighter 2, monk 2, paladin 2, ranger 3, rogue 4, sorcerer 2, warlock 2, wizard 2.
  `creationSkillChoice(entries)` soma as quantidades do multiclasse e faz a UNIÃO
    das listas (lista vazia em qualquer classe ⇒ qualquer perícia vale).

10.6 MULTICLASSE (PHB cap. 6)
  A ficha guarda `classes: [{ classKey, subclass, level }]`, no máximo 4 entradas
    (MAX_CLASSES). O `level` é o nível NAQUELA classe; o NÍVEL TOTAL é a soma.
  PRÉ-REQUISITOS para ENTRAR numa classe (MULTICLASS_MINIMUM = 13):
    barbarian FOR · bard CAR · cleric SAB · druid SAB · fighter FOR **ou** DES ·
    monk DES e SAB · paladin FOR e CAR · ranger DES e SAB · rogue DES ·
    sorcerer CAR · warlock CAR · wizard INT
  `multiclassPrerequisiteLabel(classKey, abilities, entries)` devolve o texto do
    bloqueio citando CADA classe que está barrando — o PHB exige 13 na classe nova
    E também em TODAS as classes que o personagem já tem:
      "Para entrar em Ladino você precisa de Destreza 13; para continuar como
       Paladino você precisa de Força 13 e Carisma 13"
    É a mesma função usada pelo serviço (resolveClassPatch/applyLevelUp) e pelo
    `classOptions[].eligible/missing` do DTO. Classes que o personagem JÁ possui
    ficam sempre elegíveis: o pré-requisito só vale para ENTRAR numa classe nova.
  PROFICIÊNCIAS (CLASS_PROFICIENCIES em shared/classes/index.ts): cada classe tem
    `first` (conjunto completo do nível 1) e `multiclass` (conjunto reduzido da
    tabela de multiclasse, PHB p.164). A ficha grava o resultado em
    `characters.proficiencies` (JSONB). MULTICLASSE NUNCA CONCEDE SALVAGUARDAS:
    `lockedSaves`/`lockedSavesOf` usam só a PRIMEIRA classe (as de features, tipo
    'save', continuam valendo).
  PERÍCIA DE MULTICLASSE (`multiclassSkillChoiceFor`): entrar em Bardo (qualquer
    perícia), Patrulheiro ou Ladino (da lista da classe) concede UMA perícia — o corpo do
    Level Up leva `skillChoice`, validada no servidor (precisa estar em SKILL_KEYS,
    dentro da lista da classe e o personagem NÃO pode já ser proficiente nela).
  FEATURES: `getMulticlassFeatures` avalia CADA classe no PRÓPRIO nível e concatena
    (um Bárbaro 3/Ladino 2 tem as features de bárbaro até o 3 E as de ladino até o 2).
  AJUSTES: `computeMulticlassAdjustments` calcula os ajustes por classe e SOMA/
    COMBINA: toggles e recursos deduplicados por id; meleeDamageBonus, speedBonus e
    hpBonus somam; resistências unificam; critDice e martialArtsDie pegam o maior;
    Defesa sem Armadura vira lista (vale a de maior valor); abilityBonuses somam e
    abilityCaps usam o teto de menor valor; armorClassBonus/saveBonus pegam o MAIOR
    (não somam entre classes) e halfProficiencyTargets unificam.
    Os efeitos das OPÇÕES escolhidas (Estilo de Luta Defesa) entram na mesma conta,
    lendo `classState.choices`.
  ATAQUE FURTIVO: escala com o nível de LADINO — max(1, ceil(level/2)) dados d6.
  TABELA DE ESPAÇOS (`spellSlotsForClasses`) — qual tabela é usada:
    • nenhuma classe conjuradora (ou só Bruxo) ⇒ sem espaços;
    • UMA classe conjuradora ⇒ a tabela da PRÓPRIA classe (`ownCasterLevel`):
      completo = nível cheio · meio = CEIL(nível/2) · terço = CEIL(nível/3),
      e ZERO enquanto o meio-conjurador não chega ao 2º nível (Paladino/Patrulheiro)
      ou o terço-conjurador ao 3º. Ex.: Paladino 3 = 3 de 1º; Patrulheiro 5 = 4 de
      1º + 2 de 2º; Trapaceiro Arcano 4 = 3 de 1º.
      Guerreiro/Ladino SEM subclasse conjuradora não contam (Guerreiro 5 /
      Paladino 4 usa a tabela do Paladino).
    • DUAS OU MAIS classes conjuradoras ⇒ a tabela COMBINADA (`multiclassCasterLevel`):
      full = nível cheio · half = floor(nível/2) · third = floor(nível/3); cap 20.
      O arredondamento para BAIXO é exclusivo desta tabela.
    BRUXO FICA FORA das duas e usa Magia de Pacto própria: nível 1→1 espaço de 1º; 2→2 de 1º;
    3–4→2 de 2º; 5–6→2 de 3º; 7–8→2 de 4º; 9–10→2 de 5º; 11–16→3 de 5º;
    17–20→4 de 5º.
    A tabela de conjurador completo (níveis 1..20 × espaços de 1º..9º) está
    literalmente em `FULL_CASTER_SLOTS`.
  ASI/TALENTO (`asiLevelsFor` / `isAsiLevel`) — POR CLASSE, não pelo total:
    fighter [4,6,8,12,14,16,19] · rogue [4,8,10,12,16,19] · demais [4,8,12,16,19].
  TRUQUE DE SUBCLASSE: a subclasse pode SOBREPOR a conjuração da classe
    (`effectiveSpellcasting`) — Trapaceiro Arcano e Cavaleiro Arcano são
    terço-conjuradores mesmo sendo classes marciais.

10.7 DADOS (shared/dice.ts)
  Sorteio com `crypto.randomInt` (nunca Math.random).
  Parser de expressão aceita "1d8", "2d6+3", "1d10 - 1" e valor fixo "4".
    Limites: 1 ≤ quantidade ≤ 50, 2 ≤ faces ≤ 1000.
  CRÍTICO: os DADOS são rolados duas vezes e o MODIFICADOR entra UMA vez só.
  Dano nunca é negativo (mínimo 0).

10.8 ESTADO DE CLASSE E AJUSTES DERIVADOS
  `classState` (JSONB) = { active: string[], used: { [id]: number } } — toggles
  ligados (ex.: Fúria) e usos gastos por recurso. Normalizado na leitura.
  `ClassAdjustments` (calculado, nunca gravado) expõe: toggles, resources,
  activeToggleIds, meleeDamageBonus, resistances, speedBonus, critExtraDice,
  unarmoredDefense(+/Ability/Base/Options), martialArtsDie, hpBonus, wildShapeCr,
  wildShapeFlying, abilityBonuses, abilityCaps.
  `effectiveAbilitiesOf` aplica os abilityBonuses respeitando os caps — é o valor
  usado em TODOS os cálculos derivados (CA, iniciativa, CD de magia); a pontuação
  gravada continua sendo a base.

10.9 DTO DERIVADO (`deriveStats` → DerivedStats)
  proficiencyBonus, modifiers (6), hitDie, lockedSaves[], sneakAttack, expertiseSlots,
  initiative, passivePerception, armorClass (detalhado),
  carryingCapacity, totalWeight, saves[6], skills[18], spellcasting{saveDC,attackBonus},
  spellSlots[], pactSlots, xpForNextLevel.
  REGRA: nada disso é gravado no banco; é recalculado em toda leitura.

10.10 VÁRIOS TIPOS DE DANO POR ATAQUE E POR ARMA
  Um ataque (da ficha ou de criatura) e uma arma do catálogo podem dar MAIS DE UM
  TIPO de dano, cada um com os seus próprios dados — é o que permitirá, no futuro,
  resolver cada parcela contra a resistência/imunidade do alvo (cortante 5 entra,
  necrótico 5 não, num alvo imune a necrótico).

  FORMATO (o mesmo nos três lugares, `shared/attacks.ts`):
    • `damage`       = dano PRINCIPAL — inalterado, e o que o combate rola hoje;
    • `extraDamages` = lista dos ADICIONAIS, cada um um `Damage` completo
                       ({ count, sides, bonus, type }), teto MAX_EXTRA_DAMAGES (10).
    Ataques: `attackSchema` (ficha e criaturas). Armas: `details.extraDamages`
    (categorias Arma e Cajado — o `sanitizeItemDetails` mantém a chave).

  HELPERS (para o combate novo e para a interface não repetir a regra):
    `attackDamages(attack)`   → [principal, ...extras] (o que o combate vai percorrer)
    `damageIsEmpty(damage)`   → não rola dado nenhum e não soma bônus
    `damagesExpression(lista)` / `damageExpression(dano)` → só exibição

  REGRAS ATUAIS (deliberadamente parciais):
    • o combate resolve APENAS `damage`; `extraDamages` NÃO é somado nem resistido
      ainda — o dado existe e trafega (ficha, derivados e criaturas), mas quem
      aplica cada tipo por si é a próxima etapa;
    • o ataque DERIVADO da arma equipada (`weapon-attacks.ts`) copia os
      `extraDamages` da arma, então a ficha lista "1d8 Cortante + 1d6 Fogo";
    • nenhum tipo é proibido: repetir o mesmo tipo em dois danos é válido (dois
      danos de Fogo independentes) e não há relação com as resistências do alvo.

  INTERFACE (sem poluir): a linha de dano continua como estava e ganhou um "+" ao
  lado, que acrescenta uma linha de dano ADICIONAL (mesmos campos + o tipo, com o
  "×" para remover). Vale na tabela de ataques da ficha (e do bestiário) e no
  editor de arma do catálogo (o "+" fica junto de Dados/Dado/Tipo). Cobertura na
  seção 29 do smoke.


================================================================================
11) MÓDULO characters — SEMÂNTICA EXATA DA FICHA
================================================================================

11.1 ATOMICIDADE E CONCORRÊNCIA
  Level Up roda dentro de `prisma.$transaction` com `updateMany` cujo `where` inclui
  o `lastLevelUpRelease` LIDO. Se outra requisição já aplicou, nenhuma linha casa
  (`count === 0`) ⇒ 409. Isso impede dois cliques simultâneos consumirem a mesma
  liberação. Todas as mutações de ficha incrementam `version` (`{ increment: 1 }`),
  que é o critério de ordenação de eventos no cliente.

11.2 PATCH DA FICHA — CAMPOS E VALIDAÇÕES
  Escalares copiados direto (SCALAR_KEYS): name, race, background, alignment,
  experience, 6 atributos, hpCurrent, hpMax, hpTemp, initiativeBonus, speed,
  avatarUrl, notes.
  Tratamento especial:
    • level       → SEMPRE RECUSADO (400 "O nível do personagem só muda pelo Level Up.").
                    Existe no schema só para gerar uma mensagem clara.
    • classes     → ver §11.3.
    • saves       → as salvaguardas da PRIMEIRA classe são FORÇADAS a true
                    (lockedSaves = primeira classe + efeitos de features tipo 'save').
                    Multiclasse nunca concede salvaguardas (PHB p.164).
    • skills      → substituição integral, normalizada para as 18 perícias.
    • proficiencies → substituição integral normalizada ({ armor, weapons, tools },
                    só texto, sem repetição). CONSTRUÇÃO: entra sozinho com a primeira
                    classe e pelo Level Up de multiclasse; o jogador com a criação
                    finalizada não altera (403).
    • inventory / attacks / features / classState → substituição integral.
    • spells      → se o patch vem do JOGADOR e a criação está finalizada, aplica
                    `mergeSpellUsage`: só `used` de cada nível é aceito (limitado
                    entre 0 e `max`); a LISTA de magias e o `max` de cada espaço
                    são preservados (vêm da classe/Level Up).
    • armorClassOverride → grava `armorClass` (null ⇒ 0 = automático).
  Regras de negócio embutidas:
    • Primeira classe (ou troca dela no assistente no nível 1) define o PV inicial
      pelo dado de vida máximo + mod. CON, SALVO se o patch já mandou `hpMax`, e
      grava as proficiências iniciais completas daquela classe (a menos que o patch
      já traga `proficiencies`).
    • Mudança de CON dispara o recálculo retroativo de PV (§10.4).
    • Se `classes` esvaziar, `classState` é zerado.
  Regra geral das coleções: o cliente envia o ESTADO COMPLETO da seção; não há merge
  profundo.

11.3 RESOLUÇÃO DO PATCH DE CLASSES (`resolveClassPatch`)
  Ficha SEM classe: aceita exatamente UMA classe (entra no nível 1) e EXIGE o
    pré-requisito de atributo — exceto no assistente, cuja classe é escolhida antes
    dos atributos (`skipPrerequisite`).
    Subclasse de nível 1: Clérigo/Feiticeiro/Bruxo podem (e devem, no assistente)
    trazê-la no mesmo passo; é validada por `findSubclass`. Em classe com
    `subclassLevel > 1` enviar subclasse ⇒ 400.
  Ficha COM classe: a lista só pode TROCAR A SUBCLASSE de classes existentes,
    respeitando o nível de escolha; adicionar, remover ou mudar nível ⇒ 400
    ("Para adicionar uma classe nova use o Level Up (multiclasse).").
  Substituição total da lista só é permitida ao assistente (`allowReplace`), e
    apenas quando há UMA classe no nível 1 (`canReplaceSingleClass`).

11.4 EVENTO `sheet:updated` (o mecanismo central do produto)
  Payload: { userId (DONO), username, characterId, version, changes,
             character (DTO COMPLETO já calculado), editedBy?, at }
  Destino: `toMasters` + `toUser(dono)`.
  `editedBy` SÓ é preenchido quando quem editou NÃO é o dono (ou seja, o mestre);
  a edição do próprio jogador não traz o campo.
  O DTO completo é enviado para o painel apenas substituir o estado — o cliente não
  recalcula nada.

11.5 EXCLUSÃO DE PERSONAGEM (DELETE /api/characters/:id)
  Verifica que a conta alvo NÃO é MASTER (403). Em transação:
    1. `combatant.deleteMany` por `ownerUserId` OU `characterId` (evita combatente
       fantasma na ordem de turnos);
    2. `user.delete` — a ficha sai em cascata.
  Depois: apaga o avatar do disco, limpa o estado de sessão do usuário
  (`clearActiveRollFrom` e `forgetRollsFrom`), publica `character:deleted` para mestres e
  para o dono e, após 250 ms (`unref`), `disconnectUser` derruba as conexões dele.
  Como `authenticate` confere a conta no banco, o token remanescente passa a dar 401.

11.6 INVENTÁRIO ESPELHADO (`inventory-sync.ts`)
  O inventário guarda SÓ o que é do jogador: `itemId`, `quantity`, `slot`,
  `backpackX/Y`, `id` local. Nome, descrição, peso, categoria, sprite e `details` são
  LIDOS DO CATÁLOGO ao montar o DTO (`syncInventory`). Efeito: corrigir um item no
  catálogo atualiza TODAS as fichas que o possuem (`republishSheetsWithCatalogItem`).
  Se o item saiu do catálogo, a cópia do inventário é mantida (a ficha não perde nada).
  SLOTS (estilo Tibia, 9 posições): helmet, necklace, chest, ring1, ring2, hand1,
  hand2, legs, boots. `slot: null` = mochila. Limite de 300 itens no array.

11.7 TRAVAS DO JOGADOR (`assertPlayerCanPatch`) — não valem para o mestre
  • CA manual é SEMPRE 403 para o jogador (a CA dele é calculada).
  • O INVENTÁRIO é SEMPRE 403 para o jogador, em QUALQUER fase (inclusive com a
    criação aberta): ele só muda pela movimentação (`POST /me/inventory/move`,
    que nunca toca a quantidade), pelo uso de consumível (`POST /me/inventory/use`)
    e por itens que o mestre envia. Remover item e mudar a QUANTIDADE são do mestre
    (PATCH da ficha, com `sheet:updated` para o dono).
  • Com `creationFinalized = true`, o jogador só pode alterar PLAYER_STATE_KEYS:
      hpCurrent, hpTemp, notes, avatarUrl, classState, spells
    Qualquer outro campo ⇒ 403 com a lista legível dos campos bloqueados (mapa
    CREATION_FIELD_LABELS traduz a chave para o nome em português).
  Racional: identidade, atributos, proficiências, classes, PV máximo, CA, magias,
  ataques, características e inventário são CONSTRUÇÃO — só mudam pelo Level Up ou
  pelo mestre. O que resta é o ESTADO DE JOGO.

11.8 MÓDULO (não há serviço de domínio para "recalcular ficha")

12.1 FLUXO NORMAL — POST /api/characters/me/level-up
  Entrada (levelUpSchema): { classKey, subclass? (default ''), hp: 'roll'|'average',
    skillChoice? (default '', perícia da entrada por multiclasse),
    abilityIncreases?: [{ ability, amount }] (máx. 2), feat?: { name, description }
    | null }
  Pré-condições verificadas:
    1. Nível total < 20;
    2. classe conhecida;
    3. a classe escolhida não está no nível máximo;
    4. se for classe NOVA (multiclasse), o pré-requisito de atributo deve passar
       nela e em todas as classes atuais (PHB cap. 6);
    5. **a liberação da mesa**: `character.lastLevelUpRelease <
       GameConfig.levelUpRelease` — senão 409 "Você já usou esta liberação de
       Level Up." Não existe mais nenhuma checagem de "bloqueado".
  Aplicação (uma transação):
    • `newClassLevel` = nível atual da classe + 1 (ou 1 se for nova);
    • PV do dado: se 'roll' → crypto.randomInt(1, dado+1); se 'average' → média;
    • SUBCLASSE: se a classe ainda não tem e `newClassLevel >= subclassLevel`, exige
      `subclass` no corpo (400 se faltar; 400 se não existir no catálogo);
    • PROFICIÊNCIAS: só ao ENTRAR numa classe NOVA — `data.proficiencies` =
      merge(normalizeProficiencies(character.proficiencies), grant), em que o grant é
      `multiclassProficiencyGrant` (ou `firstClassProficiencies` quando a ficha ainda
      não tinha classe nenhuma);
    • PERÍCIA DE MULTICLASSE: se a classe nova concede perícia
      (`multiclassSkillChoiceFor`), `skillChoice` é OBRIGATÓRIA (400 vazia, fora de
      SKILL_KEYS/da lista da classe ou já proficiente) e a perícia escolhida entra em
      `data.skills`; mandá-la em outro caso ⇒ 400;
    • ASI/TALENTO: se `isAsiLevel(classKey, newClassLevel)`:
        – com `feat`: empurra uma característica { id: 'feat-<uuid>', name, source:
          'feat', description } em `features`;
        – sem `feat`: as `abilityIncreases` precisam somar EXATAMENTE 2 pontos e
          nenhum atributo pode passar de 20 (400 caso contrário);
      se NÃO é nível de ASI e vier feat/abilityIncreases ⇒ 400;
    • `hpGained = max(1, dado + mod. CON já atualizado)`; delta retroativo de CON
      sobre o nível total ANTERIOR; grava hpMax e hpCurrent (+hpGained +conDelta,
      com piso 0);
    • grava `lastLevelUpRelease = config.levelUpRelease` (consome a liberação);
    • incrementa `version`; `updateMany` condicional (§11.1).
  Publica `sheet:updated`.

12.2 LIBERAÇÃO DE LEVEL UP (game-config) — SEMÂNTICA ATUAL
  `POST /api/game/level-up` (mestre, SEM CORPO) → `releaseLevelUp()`:
    `levelUpRelease = levelUpRelease + 1` SEMPRE (incremento atômico).
  REGRAS DE PRODUTO:
    • Cada clique é UMA liberação nova: habilita o botão Level Up para todos os
      jogadores que ainda não subiram naquela liberação.
    • NÃO existe estado "bloqueado" e NÃO é preciso bloquear antes de liberar de
      novo — basta clicar outra vez.
    • Um jogador sobe UM nível por liberação (comparação
      `lastLevelUpRelease < levelUpRelease`).
    • O DTO da configuração NÃO tem mais o campo `levelUpUnlocked` (removido do
      schema por migration).
  Cliente (ficha do jogador): `levelUpAvailable = lastLevelUpRelease < levelUpRelease`.
  Dica de UI: "O mestre liberou o Level Up!" / "O mestre ainda não liberou nenhum
  Level Up nesta mesa." / "Você já usou esta liberação. Aguarde o mestre liberar de
  novo." Painel do mestre: botão único "LIBERAR LEVEL UP" com o contador de
  liberações ao lado; cada clique publica `game:config` para a mesa.

12.3 NÍVEL INICIAL DA MESA (startingLevel)
  `POST /api/game/starting-level` { level: 1..20 } (clamp no servidor).
  Vale para as PRÓXIMAS criações: o passo 8 do assistente aplica os níveis 2..N.
  Não afeta fichas já finalizadas e NÃO consome a liberação de Level Up do jogador
  (`consumeRelease: false`). Fica na aba "Mesa" do painel.

12.4 LEVEL UP "DE CRIAÇÃO" (`levelUpDraft`)
  Mesmo núcleo (`applyLevelUp`), com `consumeRelease: false`, exigindo
  `creationFinalized === false` e nível total < startingLevel. É o que permite ao
  jogador montar um personagem de nível inicial alto sem depender do mestre.

12.5 HISTÓRICO DO NÍVEL (o que cada nível concedeu)
  Todo nível ganho (Level Up normal ou de criação) grava UM registro em
  `characters.levelHistory` (JSONB), no MESMO `updateMany` que aplica o nível:
    { classKey, classLevel, totalLevel,
      hp: { rolled, die, gained, conDelta, total },
      abilityIncreases: [{ ability, amount }], feat: { id, name } | null,
      choices: { [featureId]: [opções] }, subclass, skills: string[],
      proficiencies: { armor, weapons, tools } | null, at }
  `hp.total` = dado (rolado ou média) + mod. CON do momento + o delta RETROATIVO de
  CON que este nível provocou nos níveis anteriores — é exatamente o que foi somado
  em `hpMax`/`hpCurrent`.
  Motivo: a rolagem de PV, o Aumento de Atributo/Talento e as escolhas não existem
  em nenhum outro lugar da ficha. Sem esse registro não há como REVERTER um nível
  (não se sabe quanto de PV aquele nível deu nem que atributo o jogador subiu).
  O JSONB é lido com `normalizeLevelHistory` (tolerante: registro malformado é
  descartado, teto de 40 registros) e exposto em `CharacterDto.levelHistory`.

12.6 DOWNGRADE DE NÍVEL — POST /api/characters/:id/level-down (MESTRE)
  Entrada (`levelDownSchema`): { classKey, hpLost?, abilityDecreases?, removeFeatId? }.
  O inverso do Level Up: tira UM nível da classe indicada e desfaz o que aquele
  nível concedeu. O núcleo é `levelDownCharacter` (characters.service.ts).
  Pré-condições:
    1. a ficha existe (404) e TEM a classe escolhida (400) — só a rota de mestre;
    2. **a ficha não pode ficar sem classe**: remover a ÚLTIMA classe (nível 1 com
       uma só entrada) é 400 (a primeira classe define PV base, salvaguardas e
       proficiências iniciais; para desmontar, o mestre usa "reabrir criação").
  Reversão, por classe:
    • classes: nível − 1; em nível 1 a entrada SAI da ficha (com a subclasse dela);
    • PV: subtrai o `hp.total` do registro (piso 1 em `hpMax`, 0 em `hpCurrent`);
    • Aumento de Atributo: subtrai os `abilityIncreases` do registro (piso 1 por
      atributo); o talento registrado sai de `features` pelo id `feat-<uuid>`;
    • escolhas de característica do nível: as chaves gravadas no registro saem de
      `classState.choices`; a subclasse escolhida naquele nível volta para '';
    • perícias concedidas naquele nível voltam a `proficient: false`;
    • proficiências: tira as do registro, mas MANTÉM as que as classes que FICARAM
      ainda concedem (`subtractProficiencies` com `classProficiencyGrant(next)`) —
      evita tirar uma proficiência compartilhada (ex.: "Armaduras leves");
    • salvaguardas: as da PRIMEIRA classe. Se a primeira SAIR da ficha, as antigas
      voltam a false e as da nova primeira são travadas (`lockedSavesOf`);
    • estado de runtime: sair a classe inteira limpa `active`/`used` dos ids das
      features/efeitos dela (`classStateIdsFor`);
    • o registro do nível perdido SAI do histórico.
  NÍVEIS ANTERIORES AO HISTÓRICO (fichas antigas): não têm registro, então o PV é
  ESTIMADO pela média do dado de vida + CON, nada mais é revertido sozinho e a
  resposta traz `warnings` dizendo isso. O mestre pode corrigir pelo corpo:
  `hpLost` (PV exato), `abilityDecreases` (Aumento de Atributo/Talento à mão) e
  `removeFeatId` (talento a remover).
  Concorrência: `updateMany` com `version` no `where` — dois cliques seguidos não
  tiram dois níveis (o segundo recebe 409).
  Resposta: { character, levelDown } — `levelDown` = { classKey, className,
  previousClassLevel, classLevel (0 = classe removida), totalLevel, classRemoved,
  hpLost, reverted: { abilities, feats, choices, subclass, skills, proficiencies },
  warnings[] }. Publica `sheet:updated` com `editedBy` = displayName do mestre.
  O que se recalcula sozinho (nada a reverter): espaços de magia, magia de pacto,
  Ataque Furtivo, proficiência, CA, ataques derivados e as features por nível —
  todos DERIVADOS das classes, como sempre. Cobertura na seção 28 do smoke.

13) ASSISTENTE DE CRIAÇÃO DE PERSONAGEM (9 passos)
================================================================================

MODELO DE ESTADO: o rascunho É a própria linha de `Character` com
`creationFinalized = false`. O JSONB `creationDraft` guarda
{ mode, step, rolls[], baseAbilities{}, skillPicks[], abilityChoices[] }.
Os campos da ficha (nome, raça, antecedente, classe, atributos, perícias) são
gravados pelos MESMOS caminhos da ficha comum (`updateDraftSheet` → patch).
`step` guarda o passo ALCANÇADO (o maior já visto) — a retomada nunca volta sozinha.
Cada passo concluído é persistido, então fechar o navegador não perde nada.

PASSO 1 — Tipo de personagem: `mode` = 'new' | 'existing'. Persistido no rascunho.
PASSO 2 — Identidade: `name` (mín. 2 caracteres), `alignment?`, `avatarUrl?`.
PASSO 3 — Raça (SELEÇÃO do catálogo, 14 linhagens). Persiste `race` e os bônus.
    Algumas raças pedem atributos À ESCOLHA (`abilityChoice`): Meio-Elfo escolhe 2.
    A escolha é validada contra `raceChoicePool` (atributos SEM bônus fixo) e
    guardada em `abilityChoices`; trocar para raça sem escolha LIMPA a lista.
    Os atributos da ficha são sempre recalculados como base + bônus racial
    (`abilitiesPatchFrom`), a partir dos valores-BASE do rascunho — voltar ao passo
    não perde o que foi rolado/digitado.
PASSO 4 — Antecedente (SELEÇÃO, 13 do PHB). Persiste `background` e aplica as
    perícias concedidas via `skillsPatch`, que as soma às escolhidas NA CLASSE sem
    consumir as escolhas dela.
PASSO 5 — Classe: `classKey` (+ `subclass` quando `subclassLevel <= 1`).
    Se a ficha já tem níveis, trocar de classe aqui é recusado (400) — a troca
    passa a ser do Level Up/mestre. O pré-requisito de atributo é conferido aqui se
    os atributos já existirem e SEMPRE no passo 6.
PASSO 6 — Atributos (base + bônus raciais + pré-requisito da classe).
    MODO 'new': só aceita distribuir EXATAMENTE os seis valores rolados.
    MODO 'existing': aceita 1..20 por atributo; fichas reabertas podem manter
    valores acima de 20 (efeitos de nível já aplicados) se forem os atuais.
    Ao final confere `multiclassMissingLabel` da primeira classe.
PASSO 7 — Perícias: valida contra `creationSkillChoice` da(s) classe(s)
    (quantidade exata e pertencimento à lista quando ela não é vazia).
PASSO 8 — Nível inicial da mesa: passo SEM campo próprio; aplica níveis via
    `POST /me/creation/level-up` (mesmo assistente de Level Up). Só avança quando
    `nível total >= startingLevel` (400 informando quantos faltam).
PASSO 9 — Revisão: `POST /me/creation/finalize` confere `missingForFinalize`
    (mode, nome, raça, escolhas da raça, antecedente, classe, SUBCLASSE quando o
    nível 1 a exige, atributos, perícias e níveis iniciais) e só então grava
    `creationFinalized = true`. `missing` é exposto ao cliente a cada leitura, com o
    texto em português e o número do passo.
REABERTURA (mestre): `reopenCreation` volta `creationFinalized` a false e re-semeia
    o rascunho com modo 'existing', valores ATUAIS como base e passo 1.
    ⚠ OBRIGATORIEDADE DA SUBCLASSE NO NÍVEL 1 vale SÓ no assistente
    (`options.allowReplace`): o seletor legado de "primeira classe" da ficha
    (IdentitySection) não tem campo de subclasse e continua permitindo preenchê-la
    depois, no campo da classe.

  • Status inicial PENDING_INITIATIVE; publica `combat:started` (mestre com payload
    completo, jogadores com as estatísticas de criatura ocultadas).

INICIATIVA
  1d20 + dexterityMod, com o dado sorteado no servidor. Sem `combatantId`, rola o
  personagem do solicitante; com `combatantId`, só o mestre (rola por criaturas e por
  jogadores ausentes). Jogador só pode rolar a própria (403). Rolar duas vezes ⇒ 409.
  Cada rolagem publica `dice:rolled` (kind 'initiative').
  Quando TODOS têm iniciativa, o combate vira ACTIVE com currentIndex 0 e round 1,
  e o servidor emite `combat:updated` + `combat:turn`.

ORDEM DE TURNOS (`orderCombatants`)
  iniciativa DESC → desempate por `dexterityMod` DESC → desempate por nome (A→Z).
  ANTES de ACTIVE a lista é mantida na ordem de criação (a tela de espera não "pula").
  O turno atual é `combatants[currentIndex]` do DTO já ordenado.

AVANÇAR TURNO (POST /api/combat/next-turn, mestre)
  currentIndex + 1; se passar do último, volta a 0 e round += 1. Publica
  `combat:updated` + `combat:turn`.

ATAQUE (POST /api/combat/attack)
  Só em combate ACTIVE. Atacante = `attackerCombatantId` (só mestre) ou o personagem
  do solicitante. Jogador só ataca com o próprio combatente (403). Alvo ≠ atacante.
  O ataque precisa existir na ficha/criatura (`combatantAttacks`).
  Resolução (dados do servidor):
    1. CA do alvo: personagem → `characterArmorClass(...).value` (calculada!);
       criatura → snapshot `armorClass` (fallback `creature.armorClass`, senão 10).
    2. `attackRoll = 1d20`; `attackTotal = attackRoll + attackBonus`;
       critical = (attackRoll ≥ LIMIAR da ficha, 20 por padrão — 19/18 com o
       Crítico Aprimorado/Superior do Campeão); hit = critical OU (attackRoll ≠ 1
       E attackTotal ≥ CA). Crítico sempre acerta, 1 natural sempre erra.
    3. Publica `dice:rolled` (kind 'attack').
    4. Se acertou, rola o DANO ESTRUTURADO do ataque (`attack.damage` =
       { count, sides, bonus, type }) — a expressão textual é derivada daí só para
       a rolagem/exibição. Dados dobrados no crítico, modificador uma vez, mínimo
       0. Soma, quando aplicáveis:
       • DADOS EXTRAS DE CRÍTICO (critExtraDice, ex.: Crítico Brutal) — só corpo a corpo;
       • BÔNUS DE DANO CORPO A CORPO enquanto o toggle exigido está ativo (ex.: Fúria) —
         não vale para arma à distância (campo `ranged` do ataque);
       • ATAQUE FURTIVO — exige o atacante ser personagem com a feature (obtida pelo
         nível de ladino) E a arma ser `finesse` ou `ranged`. As condições TÁTICAS
         (vantagem / aliado adjacente) NÃO são rastreadas: o jogador decide quando
         rolar. Cada parcela extra publica seu próprio `dice:rolled` (kind 'damage').
    5. RESISTÊNCIA do alvo (personagem com o tipo ESTRUTURADO `attack.damage.type`
       em `resistances`, ex.: Fúria) ⇒ dano dividido por 2 (`floor(total/2)`).
       `type: null` ("sem tipo") NÃO aciona resistência.
    5b. MUNIÇÃO (só PERSONAGENS): quando o ataque tem `inventoryItemId`, a arma
        apontada precisa estar EQUIPADA numa das mãos (hand1/hand2) — senão 409.
        Se ela declara a propriedade `ammunition`, 1 unidade do `ammoType` dela é
        gasta de uma pilha da categoria 'Munição' ANTES de rolar (sem munição ⇒
        409 e nada é rolado). O `attackBonus`/`damageBonus` da munição somam ao
        ataque e ao dano; a pilha que chega a 0 sai do inventário. A escolha da
        pilha (`ammoInventoryId` opcional) prefere a SEM bônus mágico e depois a
        de menor bônus. O gasto usa `updateMany` condicionado ao `version` (com
        releitura e nova tentativa), como o Level Up, e publica `sheet:updated`
        para o dono e os mestres. Criaturas nunca consomem.
        A arma não equipada também SOME da aba Ataques do jogador (filtro no
        cliente por `isWeaponEquipped`).
    6. `changeHp(alvo, −total)` e publica `combat:updated`.
  DANO ESTRUTURADO x LEGADO: o ataque guarda `damage` estruturado e, quando a
  migração (`npm run migrate:attack-damage`) não conseguiu converter a expressão
  antiga com segurança, `legacy: true` + `damageText` com o texto original (o
  mestre revisa pela ficha). O tipo é um dos 13 canônicos ou `null`.
  VÁRIOS TIPOS DE DANO (§10.0): `attack.damage` é o dano PRINCIPAL e é o único
  que o combate resolve hoje; `extraDamages` guarda os demais, cada um com os seus
  dados e o seu tipo. O passo 4 acima (e o passo 5, de resistência) continua
  lendo SÓ `attack.damage` — aplicar cada tipo de forma independente (somando o
  que passa pela resistência/imunidade do alvo) é o próximo passo do combate.
  Resultado (`AttackResolvedPayload`) é enviado DIFERENCIADO:
    • mestre: CA, hpCurrent/hpMax do alvo, tudo;
    • jogadores, quando o ALVO é CRIATURA: targetArmorClass/targetHpCurrent/
      targetHpMax = null com `targetStatsHidden: true`.
  O corpo da resposta HTTP também é filtrado pelo papel de quem pediu.

DANO E CURA (`changeHp`) — caminho único, usado por ataque e ajuste manual
  • PERSONAGEM: dano consome PRIMEIRO os PV TEMPORÁRIOS; só o excedente chega ao
    hpCurrent. Cura (delta positivo) NÃO mexe nos temporários. hpCurrent é limitado
    entre 0 e hpMax; incrementa `version`.
    Depois publica `sheet:updated` (o jogador vê o próprio HP mudar na hora e o
    mestre vê no painel) — o combate reaproveita o canal da ficha.
  • CRIATURA: mexe só no snapshot do COMBATENTE (o bestiário não é alterado).
  • Retorna null se a origem desapareceu; o ajuste manual responde 409 nesse caso.

AJUSTE MANUAL DE HP (POST /api/combat/hp, mestre) — { combatantId, amount, mode }.
ENCERRAMENTO (POST /api/combat/end, mestre) — status ENDED + endedAt; publica
  `combat:ended`.

VISIBILIDADE (hideCreatureStats)
  Aplica-se ao DTO do combate e ao resultado de ataque: só as CRIATURAS têm
  hp/CA ocultos; personagens de jogador são visíveis para toda a mesa.

15) JANELA DE DADOS E APRESENTAÇÃO DE IMAGENS (estados efêmeros da sessão)
================================================================================

JANELA DE DADOS (dice)
  Modelo: um único `activeRoll` em memória (quem está rolando) e um histórico de até
  100 rolagens. O tabuleiro anunciado (`RollBoardDto`) = { pool[{sides,locked}],
  advantage, disadvantage, bonus, phase }.
  O cliente NUNCA rola: ele manda a composição do pool e o SERVIDOR sorteia.
  • Vantagem/desvantagem valem SÓ para d20: dois d20 são rolados e o que não vale é
    marcado `dropped`. Se vierem as duas, o servidor ignora as duas.
  • Anúncio de queda: `rollTableDice` marca `phase: 'tumbling'` ANTES de sortear e
    publica `dice:active`. Com uma requisição só, a ordem (queda → resultado) fica
    garantida para a mesa — nenhum espectador recebe o total antes da animação.
  • `lastRoll` fica no tabuleiro anunciado, então quem recarrega a página no meio vê
    o MESMO total, não os dados parados.
  • Roteamento da publicação: privada (só mestre) ⇒ `toUser(autor)`;
    `kind: 'creation'` ⇒ somente `toMasters` (a mesa nem sabe que houve rolagem);
    qualquer outra ⇒ `toTable`.
  • Uso de item (`rollItemEffect`, `kind: 'item'`): rola o `effectRoll` sem aviso de
    queda, entra no histórico do mestre e vai para a mesa como qualquer rolagem
    pública; sem efeito automático na ficha. Em Poção de Cura com `healingDice`
    (`recordHealingRoll`) a rolagem sai rotulada como `Cura (<nome>)` e o total é
    aplicado em `hpCurrent` na mesma operação do uso.
  • Privacidade: `isPrivate = Boolean(private) && role === 'MASTER'` — rolagem de
    jogador é SEMPRE pública.
  • O nome de quem rolou vem da FICHA (fallback: displayName do usuário), nunca do corpo.
  • Ao desconectar a última aba do usuário, a faixa é removida da mesa.
  • HISTÓRICO DO MESTRE (cliente, `dice/format.ts::rollDebug` + `DiceDock`): cada linha
    é "[Personagem]: [Perícia]: [total]" seguida da DEPURAÇÃO entre parênteses —
    cada dado com o TIPO, o bônus rotulado pela origem e os descartados:
      Umbrae: Percepção: 10 (d20 6 + 4 perícia)
      Umbrae: Rolagem livre: 17 (d20 14 + 3 bônus)
      Umbrae: Percepção: 10 (d20 6, descartado d20 2 + 4 perícia)
    O rótulo do bônus vem do `kind` (skill → perícia, save → salvaguarda, resto →
    bônus). O log é montado no CLIENTE a partir do próprio `DiceRollDto` (que já
    traz `dice[]`, `bonus` e `total`) — nenhum campo novo trafega e nenhum valor
    derivado é gravado. A rolagem de criação sai como
      "[Personagem]: Criação de personagem: [valor] (d6 6 + d6 4 + d6 2 + d6 2)"
    (os 4d6 sem flag `dropped`: o menor descartado da criação é escolha do
    assistente — `CreationDraft.rolls[].dropped` — e não a vantagem/desvantagem).
  • DUAS PORTAS PARA O MESMO LOG (cliente): (a) dentro da bandeja, abaixo dos
    dados, como sempre; (b) um painel flutuante só com o histórico, aberto pelo
    botão `Log` que fica ACIMA do botão `Dados` (components/master/RollLogPanel).
    O painel é um cartão ancorado acima da pilha de botões (não ocupa a tela,
    `max-height: calc(100vh - 12rem)` com rolagem própria). A lista é a MESMA nos
    dois lugares: `dice/RollLogList` + `historyLine`/`rollDebug` de `dice/format`.
  • PILHA FLUTUANTE (canto inferior esquerdo), de baixo para cima:
      base   → Inventário (`InventoryDock`) — botão + painel `.inv-panel`; SEMPRE
               presente (jogador e mestre)
      +1     → Dados (`DiceDock`)           — janela de rolagem
      +2     → Anotações (`MasterNotes`)    — só no mestre
      +3     → Log (`RollLogPanel`)         — só no mestre
    O passo é fixo (3.0rem) e o botão dos dados fica `.dice-fab` puro no jogador
    e `.dice-fab.is-master` (um degrau acima) no mestre. Os painéis são flutuantes
    (`.master-fab-panel`/`.inv-panel`) e abrem UM POR VEZ.

APRESENTAÇÃO DE IMAGENS (presentation)
  Estado único em memória `current`. O mestre mostra uma imagem para a mesa inteira
  (`presentation:shown`), fecha para todos (`presentation:closed`, idempotente), e
  quem conectar no meio recebe a apresentação ativa no handshake.
  `presentedBy` vem do token.

16) ARMAZÉM DE CONTEÚDO DO MESTRE
================================================================================

CRIATURAS E NPCs (creatures)
  Mesmos campos; o que separa é `kind` (CREATURE | NPC). Toda criatura exige ao menos
  UMA localidade. `derived.modifiers` traz os 6 modificadores. Ataques, resistências
  e imunidades são JSONB validados (resistências/imunidades restritas aos tipos
  canônicos de dano: Cortante, Perfurante, Concussão, Ácido, Frio, Fogo, Elétrico,
  Necrótico, Veneno, Psíquico, Radiante, Trovão, Força). Todo CRUD publica o evento
  correspondente para a sala dos mestres.
  IMPORTANTE: o bestiário é INVISÍVEL para jogadores (403 em todo o roteador).

REGIÕES E LOCALIDADES
  Hierarquia Região → Localidade (Localidade tem `regionId` obrigatório; apagar a
  região apaga as localidades em cascata). As duas têm descrição, imagens próprias
  (lista { url, name } gravada em /uploads) e a região tem `notes` do mestre.
  Ambas são invisíveis para jogadores. A localidade é o ponto de ligação com
  criaturas (N:N) e com o combate (localidade opcional da luta).

CATÁLOGO DE ITENS
  Categorias: Arma, Armadura, Escudo, Poção, Anel, Cajado, Item Geral, Tesouro, Outro.
  `sanitizeItemDetails(category, details)` mantém SÓ os campos que a categoria usa:
    Arma (damageCount, damageDie, damageType, extraDamages, attackBonus, damageBonus,
    weaponType, weaponCategory, properties, versatileDie, rangeNormal, rangeLong) ·
    Cajado (idem + spellcastingFocus) · Armadura (armorType, baseArmorClass, armorClassBonus) ·
    Escudo (armorClassBonus) · Poção (effectRoll, duration, potionCategory, healingDice) · Anel (effectRoll) ·
    demais: nenhum.
  PERFIL DE ARMA (Arma/Cajado) — o cadastro separa corpo a corpo de à distância:
    WEAPON_TYPES melee | ranged (padrão melee) · WEAPON_CATEGORIES simple | martial
    (padrão simple) · WEAPON_PROPERTIES (light, finesse, heavy, two-handed, versatile,
    thrown, reach, ammunition, loading, special) · versatileDie (dado de duas mãos) ·
    rangeNormal/rangeLong em METROS (corpo a corpo é 1,5 m; 3 m com reach).
  POTION_CATEGORIES (só a Poção): healing | enhancement | protection | mobility |
    stealth | exploration | poison | longevity — finalidade da poção, OPCIONAL e
    manual (rótulos PT em POTION_CATEGORY_LABELS, no cliente). Vive no details (JSONB).
  CURA ESTRUTURADA (só poção de Cura): healingDice { count 1..10, sides 4|6|8|10|12,
    bonus 0..20 } substitui o effectRoll no uso; o sanitize descarta healingDice quando
    potionCategory != 'healing' (o uso rola count d sides + bonus e aplica em hpCurrent,
    ver §uso de item).
  COERÊNCIA (superRefine no itemDetailsSchema; os padrões entram no sanitize):
    ammunition só em ranged E exige ammoType; versatile exige versatileDie e não
    combina com two-handed; thrown e ranged exigem os dois alcances. Dado
    incoerente ⇒ 400 na rota e `{}` no sanitize (nada é gravado pela metade).
  MUNIÇÃO (categoria própria): AMMO_TYPES Flecha | Virote | Bala de funda |
    Agulha de zarabatana; a categoria 'Munição' usa ammoType, attackBonus e
    damageBonus (munição mágica +1/+2/+3).
  ARMOR_TYPES: Leve | Média | Pesada — usado no cálculo de CA (§10.3).
  RARIDADE E SINTONIZAÇÃO (propriedades do ITEM, não da categoria):
    ITEM_RARITIES: common | uncommon | rare | very_rare | legendary | artifact
    (valores internos; os rótulos PT — Comum, Incomum, Raro, Muito Raro, Lendário,
    Artefato — ficam no cliente). rarity fica NULL quando o item não é classificado.
    requiresAttunement é um booleano MANUAL do mestre: nenhuma regra liga raridade
    a sintonização. itemRarityOf converte o valor do banco para a raridade válida.
    A antiga chave `details.attunement` (só Anel) foi INCORPORADA a este campo
    global pela migração 20261002010000_item_rarity_and_attunement (os anéis com
    sintonização ficam requiresAttunement = true; a chave sai do JSONB).
    ESPELHO: CatalogSnapshot/syncInventory copiam rarity e requiresAttunement para
    o inventário do jogador (InventoryItemDto), então a ficha mostra os dois.
    CORES (dnd.ts): ITEM_RARITY_COLORS é a FONTE ÚNICA — common #BDBDBD,
    uncommon #4CAF50, rare #2196F3, very_rare #9C27B0, legendary #FF9800,
    artifact #D32F2F. rarityColor/rarityTint/rarityLabel normalizam o valor
    (aceitam "common"/"Comum"/"COMUM") e devolvem estilo NEUTRO sem raridade.
    A cor aparece no texto e como detalhe discreto (anel da célula, borda do card
    do mestre e do modal); o nome da raridade segue escrito (acessibilidade).
  PREÇO (priceGold/Silver/Copper) é informação EXCLUSIVA do mestre: o DTO de jogador
  sai sem ele. O item entregue ao jogador NUNCA leva o preço.
  VISIBILIDADE: catálogo é legível por qualquer autenticado; criar/editar/remover/
  enviar é do mestre.

COMPÊNDIO (somente leitura)
  Ver §8.12. Alimenta a aba "Mesa" do painel do mestre junto do NÍVEL INICIAL.
  Fonte única: `getCompendium()`. [LACUNA] magias: estrutura pronta, lista vazia.

UPLOADS / ARMAZENAMENTO DE ARQUIVOS
  Imagens chegam como DATA URL (base64) dentro do JSON — evita dependência de
  multipart e funciona igual em dev e após o build.
  Formatos: PNG, JPEG, WEBP, GIF. Máximo 5 MB JÁ DECODIFICADOS. Nome do arquivo é um
  UUID com a extensão do mime. Pastas: localities, creatures, characters, items
  (valor desconhecido cai em localities).
  URL pública: /uploads/<pasta>/<uuid>.<ext> (servida com maxAge 7d e immutable).
  Remoção é best-effort e NUNCA sai da pasta de uploads (proteção contra `..`).
  NO CLIENTE, antes de enviar, a imagem é redimensionada para no máximo 1600px no
  maior lado (canvas) e recomprimida (JPEG 0.85; PNG/GIF mantêm transparência).

17) CLIENTE (React) — ARQUITETURA E FLUXOS
================================================================================

17.1 COMPOSIÇÃO
  main.tsx → initTheme() (aplica data-theme antes do primeiro render; o index.html já
  evita o flash) → unlockAudioOnFirstGesture() → <App/>.
  App.tsx: <AuthProvider>{loading ? splash : user ? (role === 'MASTER' ?
  <MasterPanel/> : <SheetPage/>) : <AuthPage/>}</AuthProvider> embrulhado por
  <LightboxProvider>.
  NÃO HÁ ROTEADOR DE URL: a "navegação" é por papel do usuário e por estado interno
  (abas do painel, passos do wizard, modais).

17.2 SESSÃO E TRANSPORTE
  api.ts: wrapper de fetch com 'Content-Type: application/json' e
  `Authorization: Bearer <token>` (token em localStorage, chave 'grimorio.token').
  Erros viram `ApiError` com `status`; `describeError` traduz `message` e `issues`
  (Zod) em texto legível.
  auth.tsx: ao abrir, se há token, chama GET /api/auth/me; falha ⇒ descarta o token.
  socket.ts: `io({ auth: { token }, transports: ['websocket','polling'] })` SEM URL —
  em dev o Vite faz proxy de /api e /socket.io para 127.0.0.1:3000; em produção tudo é
  mesma origem.
  useRealtime.ts: cria o socket uma vez e assina TODOS os eventos; os handlers vivem
  em uma ref, então trocar de handler NÃO reconecta. Devolve { connection, online,
  lastEventAt }.

17.3 PÁGINAS
  SheetPage (jogador)
    • Carrega a própria ficha, a configuração da mesa e os itens; assina o tempo real.
    • `needsWizard = !loading && (!character || !character.creationFinalized)` ⇒
      renderiza o cabeçalho do app (AppHeader) + CreationWizard em `.creation-shell`.
      A criação NÃO esconde o cabeçalho (tema, som, presença continuam acessíveis).
    • Com a ficha pronta, exibe SheetView com as seções.
    • Level Up: `levelUpAvailable = lastLevelUpRelease < levelUpRelease`, com dica
      textual conforme o caso (§12.2); o diálogo (LevelUpDialog) ABRE NA CLASSE
      PRINCIPAL (a lista com as classes atuais e as novas só aparece pelo botão
      "multiclasse" do cabeçalho, à direita, ao lado do X que fecha — Esc fecha
      também) e conduz subclasse quando liberada, PV (rolar/média), ASI ou Talento.
      Confirmado, a janela não fecha: troca o formulário pelo resumo do que foi
      escolhido e das características (com a descrição do livro) e PV que o nível
      trouxe — é por isso que ela segue montada com `levelUpOpen`, sem depender de
      `levelUpAvailable`.
  MasterPanel (mestre)
    • Abas: Fichas · Criaturas · NPCs · Regiões · Itens · Mesa. Em modo de combate o
      painel inteiro dá lugar ao CombatTracker.
    • Na barra de abas ficam também: botão "LIBERAR LEVEL UP" (com contador de
      liberações) e "COMBATE".
    • A aba "Mesa" contém o NÍVEL INICIAL da mesa e o compêndio (classes, raças,
      antecedentes, magias) — consulta, somente leitura.
    • A aba "Itens" (catálogo) tem, ACIMA da lista, o painel "Entregar moedas"
      (CoinsGrantPanel): escolhe o jogador, aceita valor por denominação (positivo
      dá, negativo retira), mostra o saldo ATUAL → DEPOIS e usa o
      `POST /api/characters/:id/coins` — o mestre não precisa mais abrir a ficha
      do jogador (nem entrar em modo de edição) para entregar dinheiro. A ficha
      devolvida é adotada pela lista (`adoptCoins`) e o jogador recebe o mesmo
      dado por `sheet:updated`.
    • Carga inicial em um Promise.all: characteres, creatures, regions, localities,
      items, combate ativo, configuração da mesa.
    • Todas as mutações são OTIMISTAS (a tela muda na hora e a resposta do servidor
      confirma); em erro a lista é recarregada para desfazer.
    • O mestre mantém `characters` sincronizado por `sheet:updated` (aceita a versão
      mais nova por `version`), `character:deleted` remove da lista e refresca o
      combate.
  Aba "Mesa" (ConfigTab) — carrega o compêndio SOB DEMANDA (só ao montar a aba) via
  GET /api/compendium; o nível inicial usa campo local confirmado com Enter/blur
  (evita uma requisição por tecla).

17.4 SEÇÕES DA FICHA (components/sections)
  Personagem (Identity: foto + identidade, classes, subclasse e, no FIM da seção,
  Vida e Defesa EMBUTIDA), AbilityCards (os SEIS atributos, cada um com a
  salvaguarda e as perícias dele), Attacks, Features, Spells (list + slots, com o
  bloco de Conjuração), Inventory (grade de mochila + 9 slots arrastáveis),
  Notes, BagList.
  INVENTÁRIO — HOVER x CLIQUE: passar o mouse abre um painel flutuante de
  pré-visualização (com os controles de quantidade/usar/remover); clicar abre a
  ficha detalhada no modal centralizado `ItemDetailModal` (lê o próprio item —
  nunca o preço; para o JOGADOR, consumível mostra o botão "Usar", que consome
  1 unidade via POST /me/inventory/use — o mestre não vê o botão). Fecha por X,
  clique na área escurecida ou Esc. A imagem ampliada reusa o lightbox único.
  A ficha é uma PILHA de seções de ponta a ponta: Personagem (que já traz Classes
  e Vida e Defesa), os seis atributos e as abas. O INVENTÁRIO saiu do fluxo: virou
  botão flutuante (`InventoryDock`) na base da pilha inferior esquerda, com o
  painel `.inv-panel` à esquerda de largura justa. O painel começa só com o set de
  equipamento e o peso; a MOCHILA só entra ao clicar no ícone dela no set
  (`.slot-backpack`), exibida LOGO ABAIXO do grid de equipamento, e as MOEDAS
  ficam DENTRO da mochila (campo aparte, abaixo do grid), com ícone de moeda
  colorido por denominação (ouro/prata/cobre etc.).
  IDENTIDADE (IdentitySection) — CABEÇALHO NOVO: o card do Personagem perde o
  próprio cabeçalho (`display: none`) e o avatar saiu das AÇÕES. O RETRATO
  (`.identity-section .hero-avatar`) tem `--portrait-size: clamp(8.5rem, 16vw,
  13rem)` e é ABSOLUTO em relação ao card (nenhum ancestral entre ele e a seção
  é posicionado), com `z-index: 6`. É uma FOTO CRUA: sem fundo, borda, canto
  arredondado, padding, sombra ou `filter` — o aro ornamentado já vem no

17.4.1 ATRIBUTOS EM CARDS (AbilityCardsSection)
  A antiga divisão "Atributos" (topo) + "Perícias e Salvaguardas" (lista corrida)
  virou UMA fileira de seis cards, na ordem do PHB (FOR, DES, CON, INT, SAB, CAR).
  Cada card, de cima para baixo:
    • faixa (CABEÇALHO) com a SIGLA do atributo e a pastilha dourada do "i" logo
      AO LADO dela (linha flex centrada: o "i" acompanha o título, não vai mais
      para a borda direita do card);
    • selo HEXAGONAL com o valor GRAVADO e, abaixo, o modificador — o hexágono
      fica ABAIXO da faixa, com respiro fixo (não invade o título) e usa as
      MESMAS cores da bandeirola do nome em DUAS camadas clippadas: o FUNDO é o
      fio dourado (`linear-gradient(180deg, var(--gold-bright), var(--gold-deep))`)
      e o corpo vinho vem do `::before` `inset: 1px`
      (`linear-gradient(180deg, #7d232c, #55161d 62%, #411015)`, com variante no
      tema escuro). É assim que a linha acompanha o hexágono INTEIRO, arestas
      inclinadas inclusive — uma `border` de caixa seria cortada pelo `clip-path`
      e só apareceria nas laterais. O `::before` leva `z-index: -1` (com
      `isolation: isolate` no selo) para ficar atrás do número e do modificador;
    • linha da SALVAGUARDA (caixa de proficiência + bônus + botão de rolagem);
    • as PERÍCIAS daquele atributo (FOR 1, DES 3, CON 0, INT 5, SAB 5, CAR 4,
      exatamente a divisão do PHB 2014), cada uma com caixa de proficiência,
      bônus total e rolagem.
  GRID DAS LINHAS: salvaguarda e perícias usam a MESMA grade fixa —
  [caixa 1rem] [bônus 1.7rem] [nome 1fr] [dado 1.35rem], com `gap` reduzido e
  altura mínima de 1.55rem, para todas as colunas alinharem entre os seis cards.
  O bônus é tabular e alinhado à direita. O nome NUNCA quebra no meio da palavra:
  `white-space: nowrap` + `text-overflow: ellipsis` (o nome inteiro e o que a
  perícia é vão no popup do hover) e o tamanho acompanha a LARGURA DO CARD via container query  (
  `container-type: inline-size` no card + `font-size: min(7.8cqi, 0.88rem)`),
  o que garante que "Prestidigitação" caiba até na fileira de 6 (cada card com
  ~165px, a mais apertada da ficha — nesta seção o respiro lateral do corpo é de
  0.55rem para liberar espaço ao nome). O card leva um respiro extra no pé
  (`padding-bottom: 0.55rem`) para a última linha não encostar nas rosetas dos
  cantos de baixo.
  RESUMO NO HOVER: passar o mouse (ou focar) na LINHA de uma perícia ou
  salvaguarda abre um popup com o mesmo visual do "i" (classe `info-tip-text` +
  `ability-skill-tip`), dizendo para que ela serve — os textos são
  `SKILLS[].description` (as 18 perícias) e `SAVE_DESCRIPTIONS` (as 6
  salvaguardas), em `dnd.ts`. O popup se ancora na linha, abre abaixo dela com a
  largura presa ao card e não recebe clique (`pointer-events: none`), então o
  ponteiro atravessa e troca de linha sem fechá-lo à toa.
  Os cards têm a MESMA largura e a altura do mais alto (o de 5 perícias), então os
  menores ficam com o espaço restante em branco no fim — sem esticar o espaçamento.
  As três primeiras camadas alinham entre os seis cards. Nas telas estreitas a
  fileira quebra em 3 colunas (≤1280px) e em 2 (≤720px).
  A caixa de proficiência da salvaguarda segue a MESMA lógica da perícia: fica
  desabilitada apenas para o player (`lockedConstruction`) e o mestre, em edição,
  marca à mão (`setSave` → `update({ saves })`, como `setSkill`). O servidor
  reaplica as fixas da classe (`applySaveProficiencies`), então a marcação manual
  não sobrevive à classe. Não há mais selo "classe" nem chip "esp.".
  A EXPERTISE (Ladino 1º/6º, Bardo 3º/10º) é escolhida no Level Up/criação (2
  perícias OU ferramentas entre as que o personagem JÁ domina) e vive em
  `classState.choices` + `skills[].expertise`; a ficha expõe `expertiseSkills`
  (chaves de perícia e/ou `tool:<rótulo>`). A perícia em Expertise ganha uma
  coroa de louros dourada AO LADO DO NOME (uma pastilha `.info-tip`, com o
  tooltip compartilhado de fundo sólido: "Expertise (bônus de proficiência
  dobrado)"), com brilho no hover/foco; a proficiência dela fica travada (o
  servidor recusa tirar com 400). A caixa de proficiência é o checkbox
  QUADRADO padrão da ficha. Ferramentas em Expertise ganham o mesmo selo na
  lista (são visuais).
  ROLAGEM: o botão de dado de cada linha abre a janela com 1d20 + o bônus (kind
  `skill`/`save`, como antes). No SELO, clicar no número rola um TESTE PURO do
  atributo (1d20 + modificador) — exceto para o mestre em edição, que continua
  clicando para alterar o valor bruto; o modificador também é clicável e rola.
  O "i" é uma pastilha dourada ao LADO da sigla, no CABEÇALHO do card, fora do
  selo hexagonal; a JANELA do "i" é irmã da pastilha, então se posiciona pelo
  CABEÇALHO e abre logo abaixo dele, com a largura do próprio card — nunca vaza
  para os lados.
  Ela NÃO recalcula nada: monta a composição a partir do que já vem na ficha —
  valor-base do rascunho da criação (`creationDraft.baseAbilities`), bônus racial
  (catálogo de raças buscado uma vez por `GET /api/characters/me/creation` e
  cruzado com `abilityChoices`), aumentos de nível (`levelHistory.abilityIncreases`)
  e bônus de classe (`classAdjustments.abilityBonuses`, respeitando o cap); quando
  a soma não fecha com o valor gravado (ficha antiga, edição do mestre), a
  diferença aparece como "outros ajustes", para o total NUNCA mentir. Itens
  equipados não somam atributo no sistema, e isso está dito na própria janela.
  O bloco de ARMADURAS/ARMAS/FERRAMENTAS (proficiências) que vivia na seção de
  perícias continua no fim desta seção, inalterado.

    27) Ataque derivado da arma  — a arma EQUIPADA vira ataque calculado (FOR no corpo
                                     a corpo, DES à distância, a MELHOR das duas com
                                     acuidade), com proficiência por CATEGORIA e por
                                     NOME (plural/acento), dado VERSÁTIL com a outra mão
                                     livre, DUAS MÃOS recusada (400) com a outra mão
                                     ocupada, segunda arma LEVE sem o modificador de
                                     dano, variante de ARREMESSO (ranged, mas usando
                                     FOR) e GOLPE DESARMADO; tudo resolvido no combate
                                     (incluindo o Ataque Furtivo da arma sutil)
    28) Downgrade de nível        — o Level Up grava o HISTÓRICO de cada nível (PV com
        (mestre)                    o dado/rolagem, Aumento de Atributo, talento,
                                     escolhas, subclasse, perícia e proficiências);
                                     `POST /:id/level-down` devolve tudo isso (4º
                                     nível volta PV 29→20 e a CON 12→10, 3º tira a
                                     subclasse, 2º volta ao estado inicial); nível 1
                                     caindo para 0 REMOVE a classe (com perícia e
                                     proficiências de entrada) mantendo a proficiência
                                     COMPARTILHADA; a última classe do personagem e o
                                     jogador (403) são recusados; níveis sem histórico
                                     voltam 200 com `warnings` e PV estimado
    29) Vários tipos de dano       — cada dano INDEPENDENTE: o principal continua em
                                     `damage` (é o que o combate resolve hoje) e os
                                     demais vão em `extraDamages` ({count,sides,bonus,
                                     type}), teto de 10; a arma do catálogo, o ataque
                                     da ficha e o da criatura usam a MESMA lista; o
                                     item enviado e o ataque DERIVADO levam os extras
                                     juntos; o combate resolve SÓ o principal

  LIMITE OPERACIONAL: o smoke cria ~14 contas e faz ~27 chamadas a `/api/auth/*`
  por execução. Em `NODE_ENV=production` o limiter do login é 30 por 15 min, então
  as seções novas REAPROVEITAM fichas já criadas em vez de registrar contas novas —
  qualquer seção que precise de mais contas deve seguir essa regra.

  ARMADILHA OPERACIONAL: o rate limiter é em memória. Duas execuções do smoke
  seguidas podem devolver 429 no login. Reiniciar o serviço zera o contador.

19) INVARIANTES E REGRAS QUE NÃO PODEM SER QUEBRADAS
================================================================================

 1. Toda escrita de domínio é HTTP; o WebSocket só notifica.
 2. Toda escritura de ficha incrementa `version`.
 3. O nível do personagem NUNCA é editável por PATCH: é soma de `classes[].level` e
    só sobe pelo Level Up (ou pelo assistente de criação, no passo 8).
 4. `armorClass` no banco é só o override do mestre (0 = automático). O jogador
    nunca grava CA (403).
 5. As salvaguardas das classes são FIXAS e forçadas a `true` em toda leitura —
    SÓ as da PRIMEIRA classe: multiclasse nunca concede salvaguardas (PHB p.164).
5b. `proficiencies` é CONSTRUÇÃO: entra sozinho com a primeira classe e na entrada
    por multiclasse; o jogador com a criação finalizada recebe 403 (só o mestre
    edita). Nada da CA/ataque é derivado dela ainda (Fase 2).
5c. Entrar numa classe NOVA exige 13 nos atributos exigidos por ela E por todas as
    classes que o personagem já tem; a classe que ele já possui não exige nada.
 6. O ator/identidade nunca vem do corpo da requisição, sempre do token.
 7. `authenticate` confere a conta no banco em toda requisição (exclusão imediata).
 8. No máximo um combate em PENDING_INITIATIVE ou ACTIVE.
 9. O HP de personagem nunca é duplicado no combatente: é lido ao vivo da ficha.
    O HP de criatura é snapshot do combatente (cada cópia tem a própria vida).
10. Os dados (atributos, iniciativa, PV, dano, ataques) são sorteados no SERVIDOR
    com crypto.randomInt.
11. Crítico: dados dobrados, modificador uma vez.
12. Numa liberação de Level Up, cada jogador sobe no máximo UM nível.
13. Com `creationFinalized = true`, o jogador só altera PLAYER_STATE_KEYS
    (hpCurrent, hpTemp, notes, avatarUrl, classState, spells). O mestre altera tudo.
14. Excluir um personagem exclui a CONTA do jogador; a conta de MASTER nunca.
15. O inventário espelha o catálogo; o preço é exclusivo do mestre.
16. CA/HP de criaturas nunca vão para o payload de jogador (nem no combate, nem no
    resultado do ataque); CA/HP de personagens são visíveis para a mesa.

[IMPLEMENTADO] HISTÓRICO DE NÍVEL E DOWNGRADE PELO MESTRE
   (`src/modules/shared/level-history.ts` + `characters.levelHistory`): cada nível
   ganho (Level Up normal e de criação) grava o que concedeu — PV (dado/rolagem +
   CON, incluindo o delta RETROATIVO de Constituição), Aumento de Atributo ou
   Talento, escolhas de característica, subclasse, perícia de multiclasse e
   proficiências. `POST /api/characters/:id/level-down` (só MASTER) tira UM nível da
   classe escolhida e reverte exatamente isso; nível 1 → 0 remove a classe (menos
   quando é a única); a proficiência compartilhada com as classes restantes fica.
   Fichas anteriores à migração `20260929140000_character_level_history` não têm
   registro: ali o PV é estimado pela média e a resposta avisa (`warnings`). Ver §12.5
   e §12.6. Cobertura na seção 28 do smoke.
[IMPLEMENTADO] ATAQUE DERIVADO DA ARMA EQUIPADA (`src/modules/shared/weapon-attacks.ts`
   + `derivedAttacks` no DTO da ficha): a arma equipada em `hand1`/`hand2` vira um ataque
   CALCULADO (nunca gravado, como a CA), com ids estáveis — `weapon:<item>`, a variante
   `thrown:<item>` (arma com a propriedade `thrown`), `offhand:<item>` (segunda arma
   LEVE) e `unarmed` (golpe desarmado). Cobre: habilidade FOR no corpo a corpo, DES à
   distância e a MELHOR de FOR/DES com `finesse` (o arremesso usa FOR, mesmo sendo
   `ranged`); proficiência somada por CATEGORIA ("Armas simples"/"Armas marciais") ou por
   NOME específico, com comparação tolerante a plural/acento ("Espadas longas" casa
   "Espada longa"); dado VERSÁTIL quando a outra mão está livre; arma de DUAS MÃOS com a
   outra mão ocupada listada com `blocked` (o combate devolve 400 com o motivo); segunda
   arma leve com o modificador de dano omitido (salvo se negativo); e golpe desarmado
   (1 + FOR, concussão). Os ataques derivados entram em `combatantAttacks` também, então
   `POST /api/combat/attack` resolve pelo mesmo id que a ficha mostra, alimentando
   Ataque Furtivo (`finesse`/`ranged`) e Fúria (`ranged`). Cobertura na seção 27 do smoke.
[LACUNA] O compêndio é SOMENTE LEITURA. O plano declarado é o mestre poder criar e
   editar raças/antecedentes: a arquitetura já está preparada (rota única, coleções,
   `getCompendium()` como fonte trocável), mas não há CRUD nem tabelas para isso.
[LACUNA] Ataque Furtivo não verifica condições táticas (vantagem / aliado adjacente).
[LACUNA] Não há testes unitários; a verificação é o smoke test.
[LACUNA] Presença, apresentação, janela de dados e histórico de rolagens vivem na
   MEMÓRIA do processo: não sobrevivem a restart e não escalam horizontalmente.
[LACUNA] Salas de combate (`combatRoom`) estão definidas mas não são usadas — a
   filtragem de visibilidade é feita por payload, não por sala.
[NOTA] ANOTAÇÕES DO MESTRE (`GameConfig.masterNotes`) não publicam evento: são
   texto privado de um único usuário, sem valor para a mesa. Consequência: com o
   painel aberto em DUAS abas, a segunda só vê o texto ao recarregar (e poderia
   sobrescrever o da primeira ao sair do campo). Se um dia isso incomodar, basta
   um evento exclusivo da sala dos mestres.
[HIGIENE] O único canal público além da autenticação são register/login (rate
   limited). Não há rate limit nas demais rotas.
[NOTA] `README.md`, `REVISAO-CODIGO.md` e este documento são as fontes de
   documentação; ao alterar comportamento, os três devem ser mantidos em dia.
